## المسار 0 — كيف تشتغل خوارزمية ميتا (الأساس)

> ✅ **بحث معمّق مكتمل** (run `wf_f8a8f25e-d95` — 107 وكيل، 25 ادعاءً مؤكداً، 0 مرفوض). كل بند أدناه بمصدره الرسمي واقتباسه المُتحقق. **قيد المصادر:** facebook.com/business/help يحجب الجلب الآلي (403)؛ التحقق تمّ عبر أداة مقالات ميتا المُصادَقة التي تُعيد النص الرسمي حرفياً + تعزيز مستقل من الممارسين.

### أ) المزاد — من يفوز وبكم يُدفع
- **الفائز = أعلى «قيمة كلية» (Total Value)، لا أعلى مزايدة**، فوق حدٍّ أدنى للسعر (price floor). القيمة الكلية = **المزايدة (bid) × معدل الفعل المتوقّع (estimated action rate) × جودة الإعلان (ad quality)**. [help/430291176997542]
  > «the winner of the auction is the ad with the highest total value... a combination of 3 major factors: bid, estimated action rates, ad quality.»
- **معدل الفعل المتوقّع** = تقدير ميتا لاحتمال أن يؤدّي عرض إعلانك لشخص بعينه للنتيجة المرغوبة. هو + جودة الإعلان معاً = **ملاءمة الإعلان (relevance)**، ولهذا **الإعلان الأكثر ملاءمة يفوز على مزايدات أعلى منه**. [help/1636814289727946]
- **جودة الإعلان** تُقاس من إشارات كثيرة: إخفاء/إبلاغ المستخدمين، وسمات منخفضة الجودة (حجب معلومات، لغة مثيرة، engagement bait). قياس **نسبي** مقابل المتنافسين على نفس الجمهور، **والجودة الأدنى تكلّف أكثر ⟵ توزيع أقل ⟵ نتائج أقل**. [help/423781975167984]
- **الدفع شبه ثاني-السعر بسقف:** «we'll only charge you the bid necessary to win... will not cause us to charge you more than your bid» — تدفع ما يلزم للفوز فقط، وقد يكون أقل من سقف مزايدتك.
- **تشخيصات الملاءمة (quality/engagement-rate/conversion-rate rankings) ليست مدخلات في المزاد** — أدوات تشخيص لاحقة تظهر بعد 500 ظهور فقط. لا تطاردها؛ طارد الإشارات الحيّة (الفعل المتوقّع + الجودة). [help/303639570334185]

### ب) التسليم والوتيرة (Pacing)
- ميتا تحدّد مزايدتك تلقائياً وفق استراتيجيتك، و**«الوتيرة» ترفع/تخفض المزايدة مزاداً-بمزاد وتقرّر أي المزادات تدخلها وأيّها تتخطّاها** بحسب ما تبقّى من ميزانية ووقت. شقّان كعملية واحدة: وتيرة الميزانية + وتيرة المزايدة. [help/571961726580148]
- **تصميمياً:** الوتيرة سبب كون النتائج المبكرة متقلبة وغالية — النظام «يستكشف» قبل أن يثبّت. أي تدخّل مبكر = مقاطعة الاستكشاف.

### ج) مرحلة التعلم — البند الأخطر على المصاري
- المجموعة تدخل التعلم عند إنشائها **أو عند أي «تعديل جوهري»**، وتخرج بعد **~50 حدث تحسين في الأسبوع التالي لآخر تعديل جوهري**. [help/112167992830700]
- **«التعديل الجوهري» يصفّر التعلم — وهذا تعريفه الرسمي الدقيق** [help/316478108955072]:
  - **دائماً جوهري:** أي تغيير استهداف · أي تغيير كرييتف · تغيير حدث التحسين · **إضافة إعلان جديد للمجموعة** · إيقاف المجموعة 7 أيام+ · تغيير استراتيجية المزايدة.
  - **جوهري بحسب المقدار فقط:** الميزانية وضبط المزايدة (من 100$ لـ101$ غالباً لا يصفّر؛ من 100$ لـ1000$ يصفّر).
  - **⟵ قاعدة تصميم مباشرة لـ`rules.py`:** التغذية بزيادة الميزانية لازم تكون **تدريجية (~20%)** لتبقى «غير جوهرية»، وإضافة كرييتف جديد **تصفّر التعلم** — تُجدوَل بوعي لا عشوائياً.

### د) تحسين ميزانية الحملة (CBO / Advantage+ Campaign Budget)
- **توزيع الميزانية بين المجموعات لا يُعيد أياً منها للتعلم**، و**تعديل جوهري على مجموعة واحدة لا يجرّ بقية مجموعات الحملة للتعلم** (طالما على مستوى المجموعة). لكن تغيير استراتيجية مزايدة الحملة أو تغيير ميزانية الحملة الكبير قد يُعيد عدة مجموعات. [help/316478108955072]
- CBO **يوزّع لحظياً لتعظيم الحصيلة الكلية**، لكن التوزيع **غير متساوٍ بطبعه وقد يُجوّع المجموعة الأضعف لقرب صفر إنفاق**. [jonloomer — ثقة متوسطة 2-1]
- **⟵ يؤكد قرار الدراسة:** حملة واحدة CBO بمجموعتين هو الصح؛ ولو جوّع CBO مجموعة الـLookalike مثلاً، هذا سلوك متوقّع لا خلل.

### هـ) الإشارات ومنع التكرار (CAPI)
- الخوارزمية تُدرَّب بأحداث البكسل (متصفّح) + Conversions API (خادم)، **ومنع التكرار يتم بمطابقة `event_name` + `event_id` عبر المصدرين**؛ ومسار احتياطي: `event_name` + (`external_id` أو `fbp`) بلا event_id مشترك. [developers.facebook.com/.../conversions-api/deduplicate]
- **⟵ قاعدة تصميم لـ`capi.py`:** `event_id` الحتمي المخزّن عندنا (SHA-256 لكل طلبية) صحيح ومطابق للتوصية — لكن لو أضفنا لاحقاً بكسل متصفّح لأي حدث، لازم نمرّر **نفس** event_id ليمنع التكرار.

### ⚠️ فجوات مفتوحة — تحتاج جولة بحث ثانية (Track 0.5)
البحث لم ينتج ادعاءً ناجياً على: **الـ Lookalike** (كيف تُبنى، أثر جودة/حجم المصدر) · **تداخل المزادات وتشتت الجمهور** (الآلية الكمية) · **إسناد ctwa_clid** (التدفق التقني الدقيق click→WhatsApp→conversion) · **درجة EMQ ونوافذ الإسناد** (7-day click…) · **إرهاق الكرييتف والـ frequency**. هذه محاور حرجة للمكوّنات 2/3/4 — **تُبحَث في جولة مخصّصة قبل بناء تلك المكوّنات** (مصادر أعمق: developers.facebook.com مباشرة عبر أداة مُصادَقة، Meta engineering blog، دراسات وكالات).

## المكوّنات الستة (كل بند = مسار بحث مستقل ثم بناء)

### المكوّن 1 — الكتالوج وProduct Sets · حالة: مبني جزئياً · أولوية: MVP
- **الفجوة:** لا Product Sets (نساء>بلايز/قمصان)، ورفع الـ feed يدوي، ولا مزامنة توفر تلقائية (نفاد ← إيقاف إعلاناته).
- **أسئلة البحث:** حدود الكتالوج والـ sets؛ scheduled feeds مقابل رفع يدوي مقابل API؛ قواعد فلاتر الـ set برمجياً؛ ربط نفاد المخزون بإيقاف الإعلان.
- **مصادر:** developers.facebook.com/docs/marketing-api/catalog · Commerce Manager help · product-sets API.

### المكوّن 2 — توليد الإعلانات بالجملة · حالة: مبني جزئياً · أولوية: MVP
- **الفجوة:** محور واحد (موديل×لون) بلا Product Set targeting؛ لا حملة إعادة استهداف؛ لا انتقال لهدف Purchase؛ مسار الـ SDK غير مُختبَر حياً.
- **أسئلة البحث:** هيكل حملة هدف المراسلة عبر Marketing API بالضبط؛ إعداد CTWA برمجياً (promoted_object، destination_type)؛ Advantage+ Audience مقابل Lookalike يدوي؛ سقوف adset؛ متى/كيف الانتقال لـ Purchase objective.
- **مصادر:** Marketing API campaign/adset/ad ref · CTWA setup docs · Advantage+ audience docs.

### المكوّن 3 — القياس CAPI/ctwa_clid · حالة: مبني · أولوية: MVP (صقل)
- **الفجوة:** لا حدث تصحيح استلام COD؛ لا قياس EMQ؛ لا تأكد من نافذة الإسناد.
- **أسئلة البحث:** رفع EMQ لأحداث المراسلة؛ حدث Purchase عند التأكيد + تصحيح عند الاستلام الفعلي؛ نوافذ الإسناد لـ CTWA؛ منع التكرار عبر event_id.
- **مصادر:** Conversions API for business messaging docs · EMQ guide · attribution settings.

### المكوّن 4 — البوت المحادثاتي · حالة: مفقود (الأكبر) · أولوية: MVP حرج
- **التوصية:** **هجين** — قواعد للأسئلة المتكررة (سعر، توفر، مقاسات، عرض 3 قطع) + ذكاء للغامض فقط. اختيار موديل الذكاء بند بحثي (محلي مجاني مقابل API مدفوع).
- **الفجوة:** كل شيء — لا إرسال واتساب، لا intent، لا آلة حالة محادثة، لا MPM.
- **أسئلة البحث:** WhatsApp Cloud API send + الرسائل التفاعلية + Multi-Product Messages؛ ميكانيكا نافذة الـ 24 ساعة (متى مجانية، متى قالب مدفوع)؛ تصميم intent هجين؛ مقارنة موديلات الذكاء (تكلفة/جودة/عربي/لهجة)؛ سياسة يناير 2026 (لا بوتات AI عامة — نطاق بزنس واضح).
- **مصادر:** developers.facebook.com WhatsApp Cloud API · interactive/MPM docs · messaging policy.

### المكوّن 5 — الطلب والاقتصاديات · حالة: مفقود · أولوية: MVP
- **الفجوة:** `order_cli.py` يدوي بديلاً عن آلة حالة؛ لا حساب هامش/ربح؛ لا إدارة RTO/عربون.
- **أسئلة البحث (تنفيذية أكثر من بحثية):** آلة حالة الطلب (جديد←مؤكد←مشحون←مستلم/مرفوض)؛ اقتصاديات الطلبية بأرقام المستخدم (بلوزة 85/كلفة 30، قميص 105/كلفة 40، توصيل فعلي 60/معروض 40/مجاني فوق 250، استلام 80%، كلفة طلبية إعلانية 45-55→35)؛ خفض RTO (تأكيد صريح، عنوان، عربون Bit، ذاكرة سوداء للرافض)؛ ربط نسبة الرفض بالإعلان في `rules.py`.
- **مصادر:** بيانات المستخدم الفعلية + أبحاث COD/RTO الإقليمية المحفوظة.

### المكوّن 6 — البنية والتوسّع · حالة: جزئي (SQLite فقط) · أولوية: توسّع
- **الفجوة:** لا redis (كاش/طابور)، لا تخزين كائني للصور، لا إدارة System User tokens، لا معالجة حدود المعدّل، لا تعدد أرقام.
- **أسئلة البحث:** متى SQLite يكفي ومتى ننتقل لـ Postgres/Mongo؛ Redis للطابور تحت الضغط؛ System User Token (لا ينتهي)؛ حدود معدّل Graph API؛ توسّع تعدد الأرقام تحت WABA واحد.
- **مصادر:** Graph API rate limits · System User docs · بنية النظام المرجعي (Celery/Redis/Mongo مرجّح).

## قابلية التوسّع — مبادئ محفورة من الآن

1. **مفتاح الفئة `product_type`** (نساء>بلايز...) هو محور التوسّع: إضافة أطفال/ساعات لاحقاً = Product Set جديد + فلتر، بلا إعادة بناء.
2. **بنية تحتية واحدة** (BM/Dataset/كتالوج/WABA) تخدم كل الخطوط — قرار محسوم بالدراسة.
3. **الطبقات مفصولة:** قياس/إطلاق/قتل مستقلة عن البوت — كل مكوّن يُبنى ويُختبر ويُطلق وحده.
4. **الأسرار خارج الكود دائماً** (`.env` / System User Token) — درس `credentials.json`.
